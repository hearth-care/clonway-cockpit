How to read this: dark frames are the xsource cockpit exactly as Rich will render it (palette, glyphs and footer legends match the clonway-cockpit framework — amber #d18d54, blue #7a9cc6, ❯ cursor, ▸ joints, braille spinner, no emoji). Operating model (v0.2): the Google Sheet is the operator's surface — outreach status, supplier replies, quotes and the final choice all live there, and the black book syncs from the Sheet automatically. The TUI is the engine room: fire requests, browse the black book, doctor. Outreach drafting and reply-parsing reuse Auto-Secretary's milo engine (xquill/milo/: poll-cycle daemon, compose_system_prompt stance+constitution, provenance dumps, a Safe client boundary that can draft but structurally cannot send) — xsource adds a procurement stance and a thread-watcher, not a new email stack.

Design notes

  • The research budget pill is xsource-specific: live API spend this month against config caps. Procurement is the first worker with per-run external API costs, so cost is a first-class vital sign, not buried telemetry.
  • Needs-you is the request lifecycle surfaced: any request in status open with outstanding quotes appears here, mirroring its signal.
  • Recurring-service nudges (boiler) come from black book recurs_every hints — the compounding payoff visible on day one.
  • The reply watcher pill is the health of the milo-pattern daemon that turns supplier replies into sheet rows; a stale watcher is a broken promise, so it's on the pulse.

Acceptance criteria

  • Home renders pulse, needs-you, toolkit regions via the framework home builder; assert_render_model_parity passes (human render ↔ ScreenModel kind="home").
  • Open requests with zero recorded quotes appear in needs-you with age; selecting one opens the request card.
  • Research-budget pill turns ◐ amber at 75% of monthly cap, ✗ red at 100% (and walks refuse to start new research at 100%).
  • All six toolkit entries open; no dead controls (final-boss acceptance head will drive every one).

Design notes

  • Negation tokens (NOT) get the framework’s amber _NOT_STYLE emphasis automatically.

  • Equivalent-CLI chip works as a real command with identical behaviour.

05Research — staged progress with the meter running

Standard staged-progress screen (tree connectors, braille spinner). The cap line keeps spend visible while the three discovery sources run.

walk New request                                  step 4 of 5 · q cancel

⠹ researching providers                                        00:14

  ✓ black book           1 match · Westcountry Tree Care
  ✓ Google Places        11 candidates · 8 with phone · 6 with site
  ⠹ directories          yell.com · 4 found ⠹ checkatrade.com · 3 found
  · web sweep            price ranges · local mentions · pending
  · rank & dedupe        + Companies House cross-check · pending

  caps: 6/10 Places calls · 3/8 web searches · est £0.11 this run

Design notes

  • Four-source discovery: black book → Places (structured: names, ratings, phone) → directories → web sweep (indicative price ranges, review-less locals, parish/FB mentions).
  • The directories stage is site-targeted LLM web search (site:yell.com, site:checkatrade.com + trade + town) reading their public listing pages the way a human searcher does — the long-tail coverage and vetting fidelity of those directories without scraper infrastructure. Direct APIs were verified absent (Jun 2026): Yell has none and prohibits automated copying; Checkatrade’s partner API is lead-submission only (parked, phase 4).
  • How directory parsing works: search → schema-forced extraction → code validation. The model is the parser (no CSS selectors, so site redesigns can’t break it): structured output against a fixed candidate schema where every candidate needs a source_url and every field is nullable (“report only what the listing shows”). Then deterministic validators gate entry to the shortlist: profile URL on the right domain, phone normalises as UK, rating within the directory’s native scale, dedupe vs Places. Failed fields are nulled, never guessed.
  • Companies House is demoted to a ranking cross-check: free SIC + postcode lookup that confirms legitimacy (“incorporated 2019”, flags dissolved firms) and occasionally surfaces incorporated trades with zero web presence.
  • Per-run caps are config (max_places_calls, max_web_searches); hitting a cap degrades gracefully — stage shows ⚠ capped, run continues with what it has.

Acceptance criteria

  • Each source is a separate stage; one source failing (e.g. Places 403) renders ⚠ skipped and the run still completes from remaining sources.
  • Directory-sourced candidates carry their listing URL as provenance (lands in the sheet’s Source link) and their directory rating where present.
  • Directory extraction validates in code before anything reaches the shortlist: domain-checked source_url, UK-normalised phone, rating bounds per directory scale; a candidate failing validation is dropped or field-nulled (unit-tested against recorded fixtures — tests pin the validator, not exact LLM output).
  • Cap line shows live counts; exceeding a cap never happens (assert in tests, not just UI).
  • q cancels cleanly mid-research: no sheet, no drafts, no black book writes, request not created.
  • Run cost estimate is written to obs telemetry (xops cost tracking picks it up).

Design notes

  • All side effects ride one gate — there is no path where drafts exist but the request record doesn’t. Applying also arms the reply watcher with the new thread ids.
  • money_movement: "none" is true and stays true: xsource never pays anyone; it only prepares asks.
  • Drafts-only is enforced below the gate too: SafeOutreachClient (sibling of milo’s SafeMiloClient) exposes create_draft() only — no send method exists to call. Graduating to auto-send later means consciously adding one behind this same gate, not flipping config.

Acceptance criteria

  • Agent drive without --allow-apply + token receives walk.gate and can go no further; nothing is created (the standard test_safety.py contract, extended to all three effects).
  • Grep-level guarantee in CI: no call sites for Gmail send endpoints anywhere in the package.
  • Apply is atomic-ish with honest failure: if drafts succeed and the sheet fails, result screen says exactly what exists and the request record captures partial state for retry — never a silent half-success.

Design notes

  • Column contract: worker-written — Provider, Source (linked), Rating, contacts, Indicative, Asked, Reply, Updated, and Status auto-flips (Draft ready → Asked when the watcher sees the draft sent → Replied/Quoted when a reply is parsed). Human-edited — Chosen, Notes, plus Quote £/Status for phone quotes. Fixed template, data-validated Status — the occupancy-tracker drift lesson, applied.
  • Two observability timestamps: per-row Updated (stamped on every xsource write — what happened, when) and the header-bar heartbeat (“xsource last checked HH:MM”, refreshed while the watcher polls, throttled to hourly when idle — proves the watcher is alive even when nothing changed). Reply in the inbox + fresh heartbeat + stale row = parse bug; stale heartbeat = watcher down.
  • This sheet, not a TUI screen, is where the lifecycle is read and recorded — phone-friendly, staff-shareable, zero training.
  • The bar and footer carry the request id so the sheet is always traceable back to the store.

Acceptance criteria

  • Sheet is created from a fixed template (column order, validation, footer); a golden-file test pins the layout.
  • Sync reads only the human-editable columns back into the store and tolerates unknown rows (warns, never crashes); worker columns are never overwritten by sync, human columns never by the worker (except Status auto-flips, which yield to a human-set value).
  • Sheet shares with the configured staff group on creation.

Design notes

  • The watcher is xsource’s own daemon keyed strictly by stored thread ids — it never reads milo’s forwards and milo’s operator whitelist never sees suppliers. Same reused parts: poll cycle, processed-message idempotency store, provenance dump per parse.
  • Thread capture is structural, not cosmetic: the Gmail API returns threadId at draft creation, so the request record holds it before anything is sent — no subject-line reference numbers. Replies thread via In-Reply-To/References automatically.
  • Off-thread fallback: some suppliers reply as a fresh email (quoting software, retyped address). A secondary pass matches recent messages by sender address/domain against shortlisted suppliers on open requests — flagged as “possible reply — needs a look” (needs-you item), never auto-parsed, because the match is inferred not structural. A quiet ref r-0042 in the email body footer helps this matcher and phone follow-ups.
  • Parsing is structured extraction (amount, what’s included, availability, conditions) with a no-fabrication rule: an ambiguous reply becomes Status Replied + a one-line summary; Quote £ is only filled when a number was actually quoted.
  • Sent-detection is the same watcher noticing your message on the thread — Status flips to Asked with the timestamp; nothing to record manually.
  • Phase 4 graduation: the watcher can also draft the follow-up (“thanks — when could you start?”) via the milo engine, still draft-only.

Acceptance criteria

  • A reply on a watched thread updates the correct sheet row within one poll interval; re-running the cycle is a no-op (idempotency test).
  • Emails outside watched threads are never auto-parsed; the primary watch is thread-id-bounded, and the off-thread fallback only surfaces sender-matched candidates for human review.
  • threadId is captured at draft creation and persisted on the request record before send; an off-thread reply from a shortlisted supplier’s address appears as a needs-you item within one poll interval.
  • Quoted-with-number, replied-without-number, and decline (“too busy”) replies each map to the right Status; fabricated quote values are impossible by construction (extraction schema requires a quoted source span).
  • Every parse writes a provenance JSON (raw message, extraction, sheet write) for post-hoc diagnosis.
  • Every watcher write to a row stamps that row’s Updated cell in the same batch update (a row can never change without its timestamp changing).
  • The sheet heartbeat advances on every poll cycle with live threads (throttled to hourly when no activity); the diagnostic triple — reply present, heartbeat fresh, row stale beyond one poll interval — is reproducible in an integration test and points at the provenance file.
  • Watcher stale >2h with live threads → home pill flips ◐ and an anomaly.detected signal is emitted.

Design notes

  • The sheet is the entry path; the store is the memory. Sync extracts the human-editable columns (Chosen, Quote £, Status, Notes) into the request record and supplier histories. TUI book screens are browse/QA only — [n] add note and [p] preferred remain as conveniences, never requirements.
  • Store is worker-owned JSONL at gs://clonway-orchestrator-eu-west2/state/xsource/ (suppliers.jsonl, requests.jsonl) — same bucket conventions as fleet telemetry/signals; single operator, single writer.
  • Conflict rule: human columns — sheet wins; worker columns — store wins. Deterministic, no merge UI.
  • book.import seeds from your existing black book (CSV/Sheet, one-off). book.publish renders a read-only directory Sheet for staff. Supplier records carry optional recurs_every (boiler service: 12 months) — fuel for horizon signals.

Acceptance criteria

  • Marking Chosen ✓ on the sheet → after sync: request closed, winner’s last_used + price_history stamped, losers’ quotes kept as history, needs-you and chase signal cleared. The full loop is one integration test.
  • Sync is idempotent and drift-tolerant: re-run is a no-op; a renamed/moved column warns and skips, never mis-files.
  • Round-trip property test on the store: upsert → reload → identical; corrupt line quarantined with a warning, never a crash.
  • book.search finds suppliers by name, category, or tag in <1s from local cache; offline (no GCS) degrades to read-only cache with a visible warn pill.
